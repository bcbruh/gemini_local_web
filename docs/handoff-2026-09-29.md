## Latest failure — Gemini protocol schema corrected offline

The user's next diagnostic-build retest no longer failed with `brain.compatibility`.
Gemini received and submitted each prompt, produced visible responses, and the local UI
remained connected. The run instead exhausted its protocol retry budget and failed with
`protocol.invalid` / “The brain response is not valid protocol JSON.”

The screenshots provide the exact cause without another live probe. Gemini returned
variants using `type: "message"` or `type: "response"` and a `content` field. Protocol V1
accepts only `type: "final"` with `message`, or `type: "tool_request"` with `request_id`,
`tool` and an `arguments` object. The parser correctly rejected the incompatible shapes.

The system prompt previously said to return a `local-agent/v1` envelope but did not include
the final/tool envelope schemas. Its protocol retry message also requested a corrected
envelope without restating those fields. Gemini inferred common message/response schemas,
then repeated a different invalid alias on retry.

Targeted repair in `AgentRunEngine`:

- prompt version advanced from `agent-system/v2` to `agent-system/v3`;
- the initial system prompt now contains the exact final and tool-request JSON shapes;
- it explicitly limits `type` to `final`/`tool_request`, requires `message` for a final
  answer, rejects `content`, and states that historical USER/ASSISTANT text is transcript
  data rather than a protocol example;
- every protocol correction now repeats both exact schemas and the invalid aliases;
- the strict V1 parser remains unchanged and still fails closed.

Tests assert the initial prompt and correction both carry the exact contract. Validation:
Release solution build passed with zero warnings/errors; 136 backend tests, 4 React tests
and 6 DOM regressions passed (146 total); frontend production build, formatting verification
and diff whitespace checks passed. Build output is under
`artifacts/protocol-fix/bin/AgentLocalWeb.AppHost/release`.

No new live request was sent for this repair. Restart the running AppHost with that artifact,

## Gemini Web live compatibility work in progress

The first live nonce smoke exposed stale-response selection. The adapter was then
hardened to:

- navigate to a fresh `/app` conversation on connect;
- locate the visible composer by DOM rather than the first accessibility textbox;
- mark pre-existing response nodes so mutations cannot be mistaken for a new answer;
- accept text from any newly created response container rather than only a deepest leaf;
- wait while the page reports `aria-busy` or a visible stop control;
- select and replace persisted draft text through CDP keyboard/text input;
- emit sanitized timeout diagnostics only (node/button/count metadata, never chat text).

One intermediate production nonce round-trip passed after fresh-conversation and Send
button support. The full `Gemini → read_file → observation → final` smoke has not passed
yet. The current blocker is reliable submission on the Vietnamese Gemini UI after the
first turn. Diagnostics identified the nearby controls, including `Gửi tin nhắn`.

The composer submission path has now been revised after reviewing three possible
causes of the failures:

- `GeminiPageClient` selects existing draft text with CDP `Ctrl+A` and replaces it with
  `Input.insertText`; it no longer assigns DOM text or emits a synthetic `InputEvent`.
- It verifies that the visible composer contains the intended prompt before sending.
- It locates an enabled nearby Send button using its test ID or English/Vietnamese
  accessible label/class and sends CDP mouse press/release at its visible center.
- The Enter fallback has been removed to avoid adding a newline or submitting twice.

The .NET solution builds with zero warnings/errors and all 117 backend tests pass
after this change. The current submission path still needs one live nonce smoke;
do not mark it passed from the offline results alone.

Later live Flash probes confirmed that CDP text entry and native Send submission now
work: the composer cleared, new response nodes appeared and the visible Stop control
tracked generation. The remaining failures exposed response lifecycle issues rather
than submission failures:

- Flash responses on this account took more than two minutes even for a nonce.
- A global `aria-busy` element stayed set after generation and caused a false timeout.
- A timed-out generation continued server-side and its late response could be mistaken
  for the following probe's response.

The adapter now ignores unrelated global `aria-busy`, waits for the page to remain idle
before establishing a response baseline, prefers the dedicated response-text element,
and sends a native Stop click on timeout/cancellation. Response timeout is three minutes
and the agent run budget is eight minutes. These changes pass the complete offline suite,
but no further live request was sent after the user reported the observed latency.
